# Change request: DeepSeek dialogue and real receipt analysis

Owner request 2026-09-28 supersedes the v1.1 specification where it excludes an external LLM and city comparisons. Voice, transcription, automatic complaint delivery, MAX authentication, ownership checks and VM boundaries remain unchanged. This change is open until a new release passes local, CI, VM and MAX acceptance.

## Shared contract for A, B and C

- Keep `POST /api/v1/assistant/answers` request and `AnswerView` fields compatible. With an unset topic, DeepSeek classifies intent from free text. With a selected topic, the selection wins. DeepSeek writes concise Russian dialogue grounded in the supplied facts; it never supplies arithmetic or invents a receipt, tariff, provider or cohort. A failed or missing DeepSeek call has a clear fallback response and does not block `/help` or the webhook queue.
- B owns model calls, API validation, PostgreSQL, MAX and deployment. Model: current documented `deepseek-flash`, Chat Completions JSON mode, configurable via `DEEPSEEK_API_KEY` and `DEEPSEEK_MODEL`, server only. The local `DST.txt` is a source for private runtime configuration, never a repository file or client bundle. No prompt, credential, raw PDF or unredacted response in application logs.
- C owns `housing_engine` receipt extraction and arithmetic. `EX.pdf` is a private local sample, never committed or copied to reports. It is a one-page digitally text-bearing Moscow Oblast EPD with a dense charge table, multiple totals, adjustments, reference meter table and personally identifying header/footer. Extract only the charge table and target period. Map visible row values to the existing `BillData` DTO with evidence and review flags. Preserve ambiguous columns as `null`; require user confirmation. The extracted structured snapshot already persists in PostgreSQL JSONB after review, and B may add a normalized derived aggregate table.
- For a question about a rise, B chooses the user's latest confirmed receipt and a comparable confirmed receipt for the immediately preceding calendar month with the same account/provider. C's deterministic comparison supplies deltas. If that preceding month is absent, return a short breakdown of current charges without implying a month-to-month change or adding generic next steps. If there is no confirmed receipt, say a receipt is needed. Chat and mini-app must use the same owner-scoped facts.
- City comparison is a derived aggregate only: confirmed, real, explicitly opted-in receipts; one current revision per receipt; same unambiguous city, month, service and unit. No source document, account, address, user ID or individual line is exposed across users or sent to the model. Suppress numeric results below five distinct contributors, after deletion, or when the city/metric is ambiguous. State sample size, month, metric and provenance. Synthetic preview cohorts are visibly synthetic and never mixed with real users. A user's own receipts stay private in every API query.
- A owns `apps/web/**`, restores all clarification continuations and displays compact factual answers, comparison/provenance, insufficient-data states and aggregate consent. A generic prompt requires a text input with a suggestion list for every clarification field; selected options remain available. A selected topic must remain selected after a clarification. Direct topic, unknown, contact supplier, territory, role, organization, service and document flows must all have a reachable continuation.
- Tests may use mocked model HTTP for deterministic cases, but acceptance must include one live DeepSeek smoke with the private key, read-only EX parsing check, a PostgreSQL two-user ownership/aggregate test, a mobile-width browser flow and an isolated VM deployment from an accepted release SHA. Live MAX checks still require the owner's client evidence.

2. Integrate owner-scoped latest/previous comparison, aggregate consent and city cohort queries; verify server arithmetic independent of LLM. Keep a cohort under five as `insufficient_data`.
