# Housing engine: contract v1 (E1)

The v1 DTO and JSON Schema remain unchanged. `validate_bill` and `extract_receipt` now run locally. `explain_receipt`, `compare_receipts`, `answer_question`, `compose_draft`, and `load_knowledge` still raise `NotImplementedError`; B must keep an explicit dev stub for those calls until an integrated engine release is accepted.

## Reproducible local check

From the repository root on Python 3.12 or 3.13:

```powershell
python -m venv packages/housing_engine/.venv
& .\packages\housing_engine\.venv\Scripts\python.exe -m pip install -r packages/housing_engine/requirements.lock
& .\packages\housing_engine\.venv\Scripts\python.exe -m pip install --no-build-isolation --no-deps -e packages/housing_engine
& .\packages\housing_engine\.venv\Scripts\python.exe packages/housing_engine/verify_contract.py
& .\packages\housing_engine\.venv\Scripts\python.exe -m unittest discover -s packages/housing_engine/tests -v
```

The `.venv` directory is ignored by the package's `.gitignore`. On Linux, use `packages/housing_engine/.venv/bin/python` for the same commands. `verify_contract.py` needs no DB, MAX, HTTP, network or secrets after installation. It validates the checked-in Draft 2020-12 schemas against Pydantic, validates receipt/knowledge fixtures and SHA-256 manifest, and checks the exact 200.00 → 270.00 decomposition. Any invalid fixture or changed expected result exits nonzero; the unittest changes an isolated copy of the August fixture and checks this failure path. Schemas can be regenerated intentionally with `python packages/housing_engine/verify_contract.py --write-schemas` after a reviewed DTO change.

To regenerate the synthetic PDF, raster and image-only PDF, install `packages/housing_engine/generator-requirements.lock` into the same environment and run `python fixtures/receipts/generate_demo_documents.py`. The generator updates `fixtures/receipts/manifest.json`; regeneration should leave the SHA-256 values unchanged under the pinned versions. ReportLab is used only to build checked-in fixtures, not by the engine runtime.

## Contract boundary

The only public calls are `extract_receipt`, `validate_bill`, `explain_receipt`, `compare_receipts`, `answer_question`, `compose_draft`, and `load_knowledge` (§8.2). Calls are synchronous and return Pydantic DTO, not HTTP responses. `EngineError(code,message,retryable)` reserves the eight codes in §8.3; messages must be safe to show to users. E0's `NotImplementedError` is a stage marker, not a runtime error mapping.

`DocumentInput.content` is in-memory bytes, never user JSON. `ExtractionConfig.workspace` is an existing trusted temporary job directory provided by B. OCR creates only a temporary image inside it; the package never reads a user-supplied path or makes a network request while processing. B owns original file storage, preview, user/ownership checks, queues, HTTP envelopes and MAX auth. C invokes Tesseract as a child process without shell and with a per-document timeout; B still owns the outer worker/process limit. B also owns the server-only fields `id`, `created_at`, `stale`, `stale_reasons`, and `dataset_kind` of AnswerView; `dataset_kind` of ComparisonResult; and persisted draft IDs, revisions, timestamps and stale status. B decides dataset kind from stored provenance, not from receipt text. `receipt_ref` in a request always refers to a confirmed, current revision after B's check.

DTO JSON keys use snake_case. BillData has `schema_version="1.0"`; schemas are in `contracts/engine/v1`. Every field is required unless a default is stated, with explicit `null` for unknown values. Input models reject extra keys. Money is a signed decimal string with two fractional digits, DecimalValue is a decimal string with up to six fractional digits, Period has a valid month, and UUIDs are string-encoded in JSON. Float money and guessed zeroes are invalid. A schema-valid BillData is not necessarily confirmable: `validate_bill` checks period, nonblank service name, confirmed service/adjustment amounts, stable IDs, adjustment links and printed totals. Mismatches are warnings that need acknowledgement in B, not invented corrections or an unconditional block.

`demo-bill-v1` is the English synthetic control layout in `fixtures/receipts/demo-bill-2026-08.pdf`, its PNG raster and image-only PDF. It has a `DEMO-BILL-V1` marker, period/account/issuer/address labels, one `Cold water (m3)` table line, and separately printed current charges, opening balance, credited payments, penalties, other changes, closing balance and total due. The parser requires multiple header signs and extracts values from the bytes, never from the filename. The JSON fixtures from §7.7 remain independent Russian canonical BillData for math checks. Unknown or unreadable layouts give `manual_required`/`partial`, not fabricated `recognized`. The fixture layout is not a claim of support for a real Russian bill or a phone photo.

`extract_receipt` checks byte size (10 MiB), SHA-256, MIME signature, PDF encryption/page count and image pixel count. Useful text PDFs are parsed via pypdf; a scan or image is rendered/decoded and sent to `tesseract ... -l rus+eng --psm 6` with `shell=False`. The child process receives a PNG created under `workspace`; its output is parsed using the same documented layout, with OCR evidence marked for review. `bbox` is `null` because this first path does not derive reliable positions. Missing/failed Tesseract raises a safe `EngineError(INTERNAL_ENGINE_ERROR)`; timeout uses `OCR_TIMEOUT`. B's image must include Tesseract 5 and trained data for both `rus` and `eng` and should check `tesseract --version` plus `tesseract --list-langs`. Windows E1 tests here had no Tesseract executable, so the PNG/image-only PDF tests verify only the path to the dependency error and a mocked subprocess contract; real OCR accuracy and runtime are unmeasured.

`calculate_bill` is an internal pure Decimal helper. For known line amounts it sums services plus separately recorded adjustments once. The signed balance is `opening + current + penalties + other - payments`, and total due is `max(closing, 0)`. Missing operands stay unknown. Values use `ROUND_HALF_UP` to kopecks; current charges, closing balance and total due are reconciled separately as document minus calculated. `validate_bill` returns `can_confirm`, errors/warnings and the summary reconciliation status; it does not implement a user-facing explanation.

The initial knowledge catalog has only `demo-territory`, no sources, no organizations, and no topic cards. `pilot_territory_id` remains `null` until a real territory and sources are reviewed. `contracts/engine/v1/knowledge/*.schema.json` formalizes the manifest, sources, territories, organizations, topic cards, glossary and aliases. A topic card must carry the applicability, `source_ids`, `review_after` and `content_version` described in §10.2. The E0 manifest is not a ready FAQ catalog; `load_knowledge` remains unimplemented and an empty content set must not be served as a supported answer.
