# Housing engine: contract v1 (E3)

The v1 DTO and JSON Schema remain unchanged. All seven public engine calls run locally. The E3 functions `compare_receipts`, `answer_question`, `compose_draft`, and `load_knowledge` are implemented on branch `agent-c/e3`; B should use a coordinator-accepted code SHA before enabling them in an integrated release.

`explain_receipt(ExplainRequest, KnowledgeBundle) -> ReceiptExplanation` accepts a confirmed `BillData` after B checks ownership/revision and user confirmation. It raises `EngineError(INVALID_BILL)` when required fields are absent. It uses the same Decimal reconciliation as `validate_bill`, with printed current charges distinct from the calculated balance and total due. Per-line `difference` is printed charge minus rounded quantity × tariff; `unexplained_difference` is printed total due minus calculated total due when both exist. The arithmetic explanation emits no FAQ source refs or links; `ARITHMETIC_ONLY` marks this limitation. A runnable bytes-based example is in `tests/test_e2_engine.py`: two synthetic text PDFs produce 200.00 and 270.00 explanations through the public calls. The September fixture is generated alongside August and listed with SHA-256 in the manifest.

## Reproducible local check

From the repository root on Python 3.12 or 3.13:

```powershell
python -m venv packages/housing_engine/.venv
& .\packages\housing_engine\.venv\Scripts\python.exe -m pip install -r packages/housing_engine/requirements.lock
& .\packages\housing_engine\.venv\Scripts\python.exe -m pip install --no-build-isolation --no-deps -e packages/housing_engine
& .\packages\housing_engine\.venv\Scripts\python.exe packages/housing_engine/verify_contract.py
& .\packages\housing_engine\.venv\Scripts\python.exe -m unittest discover -s packages/housing_engine/tests -v
```

The `.venv` directory is ignored by the package's `.gitignore`. On Linux, use `packages/housing_engine/.venv/bin/python` for the same commands. `verify_contract.py` needs no DB, MAX, HTTP, network or secrets after installation. It validates the checked-in Draft 2020-12 schemas against Pydantic, validates receipt/knowledge fixtures and SHA-256 manifest, and checks the exact 200.00 → 270.00 decomposition. Any invalid fixture or changed expected result exits nonzero; the unittest changes an isolated copy of the August fixture and checks this failure path. Schemas can be regenerated intentionally with `python packages/housing_engine/verify_contract.py --write-schemas` after a reviewed DTO change.

To regenerate the synthetic PDF, raster and image-only PDF, install `packages/housing_engine/generator-requirements.lock` into the same environment and run `python fixtures/receipts/generate_demo_documents.py`. The generator updates `fixtures/receipts/manifest.json`; regeneration should leave the SHA-256 values unchanged under the pinned versions. ReportLab is used only to build checked-in fixtures, not by the engine runtime. For an opt-in system OCR check after Tesseract is installed, run `python packages/housing_engine/tests/smoke_e2_ocr.py`. It checks seven synthetic PNG/JPEG/image-only PDF inputs through real bytes and reports the detected Tesseract version.

## Contract boundary

The only public calls are `extract_receipt`, `validate_bill`, `explain_receipt`, `compare_receipts`, `answer_question`, `compose_draft`, and `load_knowledge` (§8.2). Calls are synchronous and return Pydantic DTO, not HTTP responses. `EngineError(code,message,retryable)` reserves the eight codes in §8.3; messages must be safe to show to users. E0's `NotImplementedError` is a stage marker, not a runtime error mapping.

`DocumentInput.content` is in-memory bytes, never user JSON. `ExtractionConfig.workspace` is an existing trusted temporary job directory provided by B. OCR creates only a temporary image inside it; the package never reads a user-supplied path or makes a network request while processing. B owns original file storage, preview, user/ownership checks, queues, HTTP envelopes and MAX auth. C invokes Tesseract as a child process without shell and with a per-document timeout; B still owns the outer worker/process limit. B also owns the server-only fields `id`, `created_at`, `stale`, `stale_reasons`, and `dataset_kind` of AnswerView; `dataset_kind` of ComparisonResult; and persisted draft IDs, revisions, timestamps and stale status. B decides dataset kind from stored provenance, not from receipt text. `receipt_ref` in a request always refers to a confirmed, current revision after B's check.

DTO JSON keys use snake_case. BillData has `schema_version="1.0"`; schemas are in `contracts/engine/v1`. Every field is required unless a default is stated, with explicit `null` for unknown values. Input models reject extra keys. Money is a signed decimal string with two fractional digits, DecimalValue is a decimal string with up to six fractional digits, Period has a valid month, and UUIDs are string-encoded in JSON. Float money and guessed zeroes are invalid. A schema-valid BillData is not necessarily confirmable: `validate_bill` checks period, nonblank service name, confirmed service/adjustment amounts, stable IDs, adjustment links and printed totals. Mismatches are warnings that need acknowledgement in B, not invented corrections or an unconditional block.

`demo-bill-v1` is an English synthetic control layout. Six text PDFs cover 200.00, 270.00, a separate -50.00 adjustment, 100.00 opening debt with 80.00 credited payment, -30.00 closing credit, and an unknown service. Six rendered PNG/JPEG images and one image-only PDF exercise OCR; four problem files cover blank, cropped, unknown and corrupt inputs, with an additional printed-total mismatch PDF. All are listed with SHA-256 and provenance in `fixtures/receipts/manifest.json`. The parser requires the `DEMO-BILL-V1` marker plus service table headers, extracts from bytes rather than filename, and preserves an unknown service as `other` with review. The `ADJUSTMENT | amount | related_period` row is a separately printed amount and is added once to service charges; it is not embedded in the service charge. The JSON fixtures from §7.7 remain independent Russian canonical BillData for math checks. Unknown or unreadable layouts give `manual_required`/`partial`, not fabricated `recognized`. These layouts do not establish support for actual Russian bills or phone photos.

`extract_receipt` checks byte size (10 MiB), SHA-256, MIME signature, PDF encryption/page count (maximum 3), and image pixel count (maximum 25,000,000 per page). Useful text PDFs are parsed via pypdf; exact line positions are resolved through pypdfium2 and normalized to page coordinates where available, otherwise `bbox=null`. A scan or image is rendered/decoded and sent to `tesseract ... -l rus+eng --psm 6` with `shell=False`. The child process receives a PNG created under `workspace`; its output is parsed using the same layout, with every OCR value marked for review. OCR `bbox` stays `null` because the current text output has no trustworthy coordinates; page number is retained. Missing/failed Tesseract raises `EngineError(INTERNAL_ENGINE_ERROR)`; timeout uses `OCR_TIMEOUT`. `ExtractionConfig.timeout_seconds` is 1–90 seconds for the document; B owns the 120-second outer worker/process timeout and the container memory limit. The engine itself does not enforce a process RSS limit. B's image must include Tesseract 5 with `rus` and `eng` trained data, installed at build time; check `tesseract --version` and `tesseract --list-langs`. The E2 local Windows smoke used user-scoped Tesseract `v5.5.3.20260724` with both languages and recognized five synthetic rasters plus the image-only PDF; the unknown-service raster returned `partial`. This is a test of generated renderings, not real bills, phone photos, Docker or VM.

`calculate_bill` is an internal pure Decimal helper. For known line amounts it sums services plus separately recorded adjustments once. The signed balance is `opening + current + penalties + other - payments`, and total due is `max(closing, 0)`. Missing operands stay unknown. Values use `ROUND_HALF_UP` to kopecks; current charges, closing balance and total due are reconciled separately as document minus calculated. `validate_bill` returns `can_confirm`, errors/warnings and the summary reconciliation status. `explain_receipt` exposes this arithmetic for a confirmed BillData, with services and adjustments separated in `balance_components`, a line formula where supported, and no legal/source claims.

The E3 knowledge catalog has fifteen generic topic cards, controlled aliases and two definitions of application fields. Two official nationwide GIS ЖКХ citizen-help pages, actually opened on 2026-09-27, support `account_number` and `payment_history`; their SourceRefs have `territory_id=null` and only `cdn.dom.gosuslugi.ru` is in the HTTPS host allowlist. `territories.yaml` now lists the owner-selected regions `moscow` (Москва) and `moscow-oblast` (Московская область) alongside `demo-territory`; these names have `source_id=null` because they are owner-provided scope, not verified local instructions. `pilot_territory_id=null` remains until a concrete house/organization is selected. Local topics for either real region return `unsupported` without a fresh, region-specific source; the general GIS ЖКХ links remain usable. No organization, local procedure, deadline or recipient channel is verified. Generic card `review_after` remains an editorial reminder, separate from the sources' actual `verified_at` timestamps.

## E3 comparison, questions, and drafts

`compare_receipts(CompareRequest, KnowledgeBundle) -> ComparisonResult` accepts two confirmed bills after B checks ownership and current revisions. It sorts by period, rejects the same month or explicit account/provider/address conflicts with `INCOMPARABLE_RECEIPTS`, and leaves unrelated service lines unpaired. Missing identity fields with `identity_acknowledged=false` return `needs_identity_confirmation` with the missing paths and a confirmation action: all deltas are null and both `lines` and `settlement_deltas` are empty. A repeat with acknowledgement computes from the given bills but still shows `IDENTITY_UNVERIFIED`. Exact matching uses code, scope, unit, supplier, segment, and for `other` the exact normalized name/unit label. Unique cross-unit lines are `incompatible`; duplicate candidates are `ambiguous`. No fuzzy service inference occurs.

For a matched complete product, `quantity_effect = round((q_new-q_old)*t_old, 2)`, `tariff_effect = round(q_new*(t_new-t_old), 2)` and `rounding_effect = delta - both effects`. Partial inputs keep known deltas and null unavailable effects. `delta_current_charges` includes separate adjustments once; `delta_adjustments` only discloses the already included part. `settlement_deltas` keep opening balance, payments (negative contribution), penalties, other account changes, and the max(0,balance) credit clamp separate. `unexplained_delta` is computed only with both full supported formulas and known operands. Printed totals are not replaced by calculated totals. The synthetic bytes-derived PDFs demonstrate 200.00 → 270.00, delta 70.00 = volume 40.00 + tariff 30.00; `e3-settlement-comparison.json` demonstrates 200.00 → 190.00 when -50.00 adjustment and 30.00 payment act separately.

`load_knowledge(path, now)` reads only local YAML and hashes the catalog into `knowledge_version`; it makes no HTTP requests. Exactly fifteen unique cards, territory/source references, dates and HTTPS source host allowlist are checked at load. The static schema verifier checks all YAML shapes. `answer_question` uses fixed topic examples, keywords, aliases and a small reviewed family of common Russian word stems with minimum score 2 and margin 2; an explicit valid `topic_id` wins. When a question contains two supported intentions joined by «и», the engine asks which topic to use. It asks one missing context field at a time, with `document_kind` first for «справка». Unknown questions are `unsupported` or a topic clarification. Expired, synthetic, future-dated or foreign sources never become actionable instructions. The two sourced generic cards return a SourceRef and an explicit link action; local cards still give no local procedure or deadline for Moscow or Moscow Oblast.

`python packages/housing_engine/eval_questions.py` runs a fixed offline 75-question synthetic regression corpus (60 phrases across 15 topics plus 15 ambiguous/unrelated cases). Gold topic/status was committed as `66e774c123896388608fc24d6a06e1890de7bbf5` before the first evaluation. The first baseline exposed ranking failures, so later results on this same corpus are calibration checks, not an independent holdout. A separate untouched holdout is required for the §15.4 quality gate; no questions, receipts or queries are sent to a network service during the harness.

`compose_draft` uses only confirmed bill fields and the selected `line_id`; user text is quoted as unverified user wording and never interpreted as an instruction. The returned text is editable, contains no send operation, and has `recipient=null`/`RECIPIENT_UNVERIFIED` when no verified organization channel exists. B owns stale draft state and copy behavior. No real submission channel or recipient is configured in E3.
