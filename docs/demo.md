# Демонстрация помощника ЖКХ: синтетический сценарий

Текущий этап — E4. Этот сценарий описывает интерфейс развёрнутого релиза `d3fa9b2fc4ea3ae89a0691c331945d2a6d1354f9`. Перед показом ведущий записывает **фактически запущенный release SHA** и режим стенда. Проверенный Chrome/Compose dev сценарий не считается входом в MAX; работу в MAX Web и мобильном MAX отмечают только после развёртывания и регистрации mini-app.

Все суммы, организация, адрес и лицевой счёт ниже **синтетические**. В текущем каталоге `demo-territory` показана как «Учебная территория»; организация и квитанции вымышлены. Никаких реальных квитанций, учётных данных или персональных сведений на экране. Голос и отправка обращения не входят в показ.

## Подготовка стенда

1. B подтверждает принятый SHA, готовность API/worker/PostgreSQL и путь `/team/zhkh/`. На dev стенде: `GET /team/zhkh/api/v1/meta` должен сообщать `receipt_ocr=true`, `engine_stub=false`; локальный демовход допустим только если backend явно запущен с ним. В production демовхода нет: нужен связанный бот и проверенный `window.WebApp.initData`. Не публиковать код доступа, токены или URL с токеном.
2. Для предсказуемого показа используйте отдельную тестовую запись без чужой истории. Подготовьте браузер шириной не менее 360 px и второе окно с этим документом; реальные данные участников не загружайте. Если нет MAX регистрации, показывайте `dev:real` и называйте его **dev браузером**.
3. Автоматизированная репетиция доступна из `apps/web`: `npm run test:browser:e3:real` и `npm run test:browser:e4:real`. Для них снаружи Git задают `BASE_URL` (например, `http://127.0.0.1:5173/team/zhkh/`), `DEMO_ACCESS_CODE` и `CHROME_PATH`; первый скрипт проходит 200→270, FAQ и copy-only/stale, второй — отказоустойчивость. Перед запуском нужен Vite `dev:real` с прокси к Compose API. [Успешный CI E4 на синтетических данных](https://github.com/FlynnTaggart076/VK_Hackathon/actions/runs/36333584617) проверяет этот технический уровень, но не VM/MAX.

Примите показанные предупреждения, если они есть, и нажмите «Подтвердить проверенные данные». | Пометка «Синтетический пример» на проверке и объяснении; подтверждение следует после проверки человеком. |
| 2:00–2:55 | Тем же способом загрузите «Вода, сентябрь». Сверьте `2026-09`, объём `6`, тариф `45`, начисление и итог `270.00 ₽`. Для показа сохранения добавьте ` (учебная правка)` к полю «Организация», нажмите «Сохранить исправления», убедитесь в новой ревизии, затем подтвердите. | Сохранение и подтверждение — разные действия. Это **учебная текстовая правка**, а не обнаруженная ошибка OCR; суммы не пересчитываются в браузере. Код поставщика, счёт, адрес, единица и числа остаются прежними. |
| 2:55–3:35 | В «Истории» откройте «Сравнить квитанции», выберите созданные августовский и сентябрьский документы и нажмите «Сравнить». | Серверное сравнение: к оплате `200.00 → 270.00 ₽`, разница `70.00 ₽`; влияние объёма `40.00 ₽`, тарифа `30.00 ₽`. На сравнении видна синтетическая пометка. |
| 3:35–4:25 | Из сравнения нажмите «Подготовить черновик», выберите тему «Запрос расшифровки» (`request_breakdown`), подготовьте текст. Измените его, сохраните и нажмите «Копировать текст». | Факты подтверждённой квитанции видны рядом; получатель может быть не определён. Кнопки отправки нет, обращение не отправляется. |
| 4:25–5:00 | В «Помощнике» снимите выбранную тему и спросите «xyzzy неизвестное». | «Пока нет проверенного ответа», без придуманной конкретной ссылки. Завершите показ границами: учебные квитанции, самостоятельная проверка чисел, нет проверенного канала конкретной УК. |

Каталог отдаёт оба образца после входа; UI вызывает защищённый `POST /receipts/demo`. Это **серверный импорт синтетического JSON**, не OCR файла. Поэтому в основном показе не называйте уточнение сентябрьского поля «исправлением OCR». OCR синтетического PDF/PNG проверен отдельно в CI; для демонстрации именно байтового OCR нужен отдельный согласованный сценарий, а не переименование JSON импорта. Выбор образца не требует размещать PDF в `apps/web/public`.

## Если что-то пошло не так

- **Сеть:** в истории появляется ошибка и «Повторить загрузку истории». После восстановления соединения повторите запрос; сохранённые документы остаются на сервере. На загрузке файла повторяйте тот же файл только после сетевого сбоя.
- **401:** в dev войдите заново на текущем URL. В production закройте и переоткройте mini-app в MAX для свежих стартовых данных. Не пытайтесь восстановить сессию из URL или localStorage; сохранённый документ перечитывается с сервера.
- **409 ревизии:** при одновременной правке форма сообщает о новой серверной ревизии и оставляет локальный ввод. Выберите «Применить мои правки к актуальной ревизии» либо «Использовать серверную версию», затем явно сохраните и подтвердите заново. Не перезаписывайте молча чужую правку.
- **413:** файл превышает указанный на экране лимит (в текущей конфигурации 10 МБ). Выберите меньший PDF/JPEG/PNG; большой файл не ставится в OCR очередь. Не демонстрируйте отказ на реальном документе участника.
- **Неизвестный макет:** `unknown-layout.pdf` из `fixtures/receipts/` — тоже синтетический файл, но при обычной загрузке API помечает происхождение `user_provided`; это не сертификат реальности. После обработки экран показывает `manual_required` и просит ручной ввод. Для публичного основного показа используйте два каталожных образца с серверной пометкой `synthetic`.

Фактическое выполнение в MAX Web и мобильном MAX, результаты участников и дефекты записываются в [протокол пользовательской проверки](user-validation.md), отдельно от CI.
